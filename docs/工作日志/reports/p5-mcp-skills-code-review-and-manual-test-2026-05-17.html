新增功能

功能 作用 前端或 API 可见点
Capability Registry 将 builtin tool、MCP-shaped tool 和后续 skill 能力固化为可版本化能力记录。 /tools 工具运行层展示工具来源、风险、沙箱、角色和 MCP 元数据。
Agent Capability Attachment 将 Agent 能执行什么工具固定到 attachment 表，运行时不再信任 Agent.tools_json。 Workspace chat、Agent Run、assignment worker、test invoke 都通过同一 capability resolver。
Immutable Capability Version 每个工具元数据版本生成 content/config hash，ToolCall 和快照引用不可变版本。 Run Detail 的工具调用表现在展示 capability version 和 content hash 缩写。
Capability Snapshot Run、Task、ModelCall、ToolCall、Eval 记录执行当时的能力证据，支持重放和审计。 Run Detail 的工具调用表和事件流可看到执行证据。
Admin Validate / Test Invoke 区分“只校验元数据”和“以 Agent 身份试运行工具”，避免 admin 校验被误当成执行权限。 POST /api/tools/capabilities/admin-validate 与 /test-invoke。

修复的问题

1. 迁移文件不能引用运行时 ToolRegistry

问题：20260517_0018_create_capability_registry.py 原先从运行时 ToolRegistry 读取 builtin 工具并 seed migration。未来运行时代码一变，历史迁移行为也会变。

修复：迁移内置 FROZEN_TOOL_METADATA 历史快照，seed 只使用冻结数据。这样 migration 是历史记录，不再和运行时代码形成双权威。

2. Workspace chat 未授权工具不应提前变成 unknown tool

问题：Workspace chat 对“全局已知但当前 Agent 未 attach 的工具”会在 SSE 层提前返回 unknown tool，没有生成 DENIED ToolCall。权限没有被放宽，但四个入口的审计证据不一致。

修复：Workspace chat 现在对已知工具也进入 ToolRunner，由 capability resolver 统一拒绝，并写入 DENIED ToolCall。新增测试锁住不允许从 tools_json lazy backfill。

手动前端测试

入口

  1. 打开本次测试地址：http://127.0.0.1:5179。
  2. 确认页面能正常进入 Agent Console，没有空白页或全屏错误。

测试 1：工具注册表页面

  1. 进入 /tools。
  2. 确认顶部统计展示工具总数、MCP 数、需要沙箱数量、分类数量。
  3. 切换 all、builtin、mcp 筛选。
  4. 确认表格展示工具名、来源、风险、角色权限、审计级别、MCP server/method 和 input schema。

测试 2：Workspace chat 工具 mention

  1. 进入默认 Agent Workspace。
  2. 在 Plan 模式输入包含工具 mention 的目标，例如：请读取项目配置 @read_file。
  3. 发送后观察聊天流里出现工具调用请求和结果卡片。
  4. 工具 mention 语法是独立 token：@read_file、@list_files、@mcp_context_search。
  5. 如果工具需要审批，确认页面显示 pending approval，而不是直接执行。

测试 3：Run Detail 工具调用证据

  1. 从 Workspace 创建一个带工具 mention 的 run。
  2. 进入该 run 的详情页：/runs/{run_id}。
  3. 在“工具调用”表确认工具名、状态、风险、Capability version 缩写、content hash 缩写、延迟和输出摘要。
  4. 确认同一个 run 的事件流仍然正常展示，工具调用状态和聊天里看到的结果一致。

测试 4：审批可见性

  1. 在 Workspace 中输入需要副作用工具的 mention，例如：执行一次 shell 检查 @run_shell。
  2. 发送后确认聊天里出现 pending approval 状态。
  3. 进入对应 Run Detail，确认右侧审批区域出现同一条审批请求。
  4. 点击批准或拒绝，确认审批状态在页面上发生变化。
